## 配置

1. 在 [Resend](https://resend.com/domains) 添加自己持有的发信域名或子域名，例如 `auth.你的域名`。
2. 按 Resend 给出的实际 DNS 记录完成 SPF/DKIM 验证；若 DNS 在 Cloudflare，在那里添加这些记录。具体记录值以控制台为准。
3. 创建邮件发送用 API Key，并将下面两项填入项目本机 `.env`。不需要把密钥发到聊天里，也不要提交 `.env`。

```dotenv
RESEND_API_KEY=你的Resend密钥
KOTOBA_EMAIL_FROM=login@已验证的发信域名
```

`KOTOBA_EMAIL_FROM` 只填邮箱地址，显示名称由程序设为 Kotoba Live。密钥仅由服务端读取，不进入网页、扩展、错误响应或日志。

```sh
npm run account:email
```

默认地址为 <http://127.0.0.1:8792/pricing>。首次运行建立独立的 `output/account-email/` 数据库和会话密钥，不导入 `.test` 模拟账户或旧测试余额。真实发信模式缺少配置即报错退出，不回退到测试验证码。

原来的 `npm run account:test` / 8791 继续作为模拟入口，只允许 `.test` 邮箱；真实模式完全禁用读取测试验证码的接口。两种模式使用不同的 Cookie 名称、数据库和密钥。

## 发送及失败规则

- 每个邮箱至少间隔 60 秒，滚动起点的每小时窗口最多 5 次发送尝试；整个实例同窗口最多 100 次，另有 Better Auth 请求限频。失败尝试也占用限额，避免供应商故障时持续重试。
- 限频在生成新验证码前检查，被限频拒绝不会使上一条验证码失效。正常重发会生成新验证码，旧码随之失效。
- 发送计数持久保存，重启不能绕过；只保留邮箱哈希，不在限频表保存邮箱明文。邮箱哈希不是匿名数据。超过 24 小时无活动的记录在后续发送时清理。
- 网络请求最长等待 10 秒。供应商拒绝、超时或异常响应返回统一错误；不自动重试发送。用户可以等倒计时结束后手动重发。
- 每次发送带独立的 Resend 幂等键。供应商接受请求才向页面报告“已提交发送”，不等于进入收件箱；超时也不证明绝对未发送，若已收到验证码仍可尝试登录。
- 前端显示重发倒计时和明确失败提示。验证码不放在邮件主题、URL或页面中；邮件正文明确有效期及忽略非本人操作的说明。
